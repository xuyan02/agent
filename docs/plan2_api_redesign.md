# Plan Tool API Redesign (Current Design)

This document records the **current agreed design** for the plan tool API redesign.

## Tool namespace
TBD: `plan.*` vs `plan2.*`.

## Core data model

### Task / Subtask fields
Applies to both top-level tasks and subtasks unless stated otherwise.

- `id`: string UUID (system-generated)
- `name`: string (required, non-empty; not required to be unique)
- `description`: string (required, non-empty)
- `goal`: string (required; MUST include DoD marker like `DoD:` / `完成标准:`)
- `depends_on`: array of sibling ids (optional)
- `state`: enum string (see below)
- `reason`: string
  - required when `state == waiting`
  - required when `state == abandoned`

Top-level only:
- `report_to`: string (required, non-empty)

Subtasks:
- `report_to` is not allowed.

### State names
Final names:
- `blocked`: dependency-blocked (derived from `depends_on`; `reason` not required)
- `ready`: executable but not started
- `active`: currently executing
- `waiting`: explicitly waiting for external info/artifact (`reason` required)
- `done`: completed (terminal)
- `abandoned`: failed/refused (terminal; `reason` required)

### State machine (summary)
Allowed transitions (others are errors):
- deps satisfied: `blocked -> ready`
- activate_task: `ready -> active`
- suspend_task: `active -> waiting` (reason required)
- resume_task: `waiting -> ready` (clears reason; must not go directly to `active`)
- complete_task: `active -> done`
- abandon_task: `* -> abandoned` (reason required; `done` is not allowed)

Additional confirmed constraints:
- Execution must not happen unless the corresponding task is `active`.
- `waiting` must go `waiting -> ready -> active` (no direct waiting->active).

## Hierarchy rules (important)

### Top-level `active` uniqueness
- At most one **top-level** task may be `active` at any time.
- Activating a top-level task implicitly switches the previously-active top-level task back to `ready`.

### Activating a subtask
- Subtasks may be activated.
- If a subtask is activated, its ancestor chain up to the top-level parent is automatically activated.
  - This may implicitly switch the previously-active top-level task to `ready` (to preserve top-level uniqueness).

## Tool functions
All functions return either:
- success: `{ "ok": true, ... }`
- failure: `{ "ok": false, "error": "..." }`

### add_task
Creates one top-level task.

Input:
```json
{
  "name": "string",
  "description": "string",
  "goal": "string",
  "report_to": "string",
  "depends_on": ["task_id", "..."]
}
```

Rules:
- `id` is generated by the system.
- `depends_on` can only reference existing top-level task ids.
- initial state is auto-computed:
  - deps satisfied => `ready`
  - deps not satisfied => `blocked`

Output:
- success: `{ "ok": true }` (no task payload)

### remove_task
Deletes a task with cascading semantics.

Input:
```json
{ "id": "uuid" }
```

Semantics:
- deletes the target task
- deletes all its subtasks (entire subtree)
- deletes the **transitive dependent closure** (any task that directly/indirectly depends on it), and their subtrees

Output:
- success: `{ "ok": true }` (no deleted id list)

### activate_task
Activates a task.

Input:
```json
{ "id": "uuid" }
```

Rules:
- requires target state == `ready`
- sets target state to `active`
- if target is a **top-level** task and there is another top-level task currently `active`, it is implicitly switched to `ready`
- if target is a **subtask**, its ancestors are automatically activated up to the top-level parent (which may cause a top-level implicit switch)

### suspend_task
Suspends an active task into external waiting.

Input:
```json
{ "id": "uuid", "reason": "string" }
```

Rules:
- requires target state == `active`
- sets target state to `waiting`
- `reason` is required and non-empty

### resume_task
Unblocks an external-waiting task back to ready.

Input:
```json
{ "id": "uuid" }
```

Rules:
- requires target state == `waiting`
- sets target state to `ready`
- clears `reason`

### complete_task
Marks an active task as done.

Input:
```json
{ "id": "uuid" }
```

Rules:
- requires target state == `active`
- sets target state to `done`

### abandon_task
Marks a task as abandoned (failed/refused).

Input:
```json
{ "id": "uuid", "reason": "string" }
```

Rules:
- requires target state != `done`
- sets target state to `abandoned`
- `reason` is required and non-empty

## Subtask functions

### add_subtask
Adds a single subtask under a parent.

Input:
```json
{
  "parent_id": "uuid",
  "name": "string",
  "description": "string",
  "goal": "string",
  "depends_on": ["subtask_id", "..."]
}
```

Rules:
- system generates subtask UUID
- `depends_on` can only reference existing sibling subtasks under the same parent
- initial state is auto-computed:
  - deps satisfied => `ready`
  - deps not satisfied => `blocked`

Output:
- success: `{ "ok": true }`

### clear_subtasks
Deletes the entire subtask subtree under a parent.

Input:
```json
{ "parent_id": "uuid" }
```

Output:
- success: `{ "ok": true }`
